# 小红书同步脚本 CDP 迁移方案

> 日期：2026-05-15
> 状态：设计完成，待实现

## 1. 背景

`xhs_playwright_sync.py` 当前使用 Playwright 启动 headless Chromium，配合大量 JS 注入代码伪装浏览器指纹。该方案在实际使用中触发了小红书的风控系统，导致账号被功能限制（不能私信、发布、评论、点赞，封禁一周）。

## 2. 问题分析

### 2.1 当前方案的问题

| 问题 | 说明 |
|------|------|
| `headless=True` | 无头模式是现代风控的基础检测信号 |
| 全新浏览器实例 | 每次启动无浏览历史、无扩展、无持久化数据，设备指纹始终为"新设备" |
| 行为模式单一 | 启动 → 采集 → 关闭，没有正常用户的上下文行为 |
| 执行频率过高 | 一天内多次执行，明显超出正常用户行为模式 |
| JS 注入伪装 | 尽管覆盖了 webdriver/chrome.runtime/WebGL/Canvas，但注入本身可被检测 |

### 2.2 账号影响

- 日常使用账号 + 脚本自动化操作 → 行为画像冲突 → 触发风控
- 功能限制一周，影响正常使用

## 3. 方案：CDP 连接真实 Chrome

### 3.1 核心思路

放弃 Playwright 启动浏览器，改为通过 Chrome DevTools Protocol (CDP) 连接用户日常使用的真实 Chrome。

### 3.2 优势

- **真实设备指纹**：UA、WebGL、Canvas、GPU、字体、插件全部真实，无需伪装
- **无自动化标记**：无 `--enable-automation` 启动参数，`navigator.webdriver` 根本不存在
- **真实浏览上下文**：Chrome profile 包含浏览历史、Cookie、扩展、登录态
- **大幅简化代码**：移除 ~100 行 stealth 伪装代码
- **Cookie 自动持久化**：登录态存在于真实 Chrome profile，无需额外的 session 文件管理

### 3.3 自动兜底机制

```python
async def _ensure_cdp():
    检查 127.0.0.1:9222 是否可连接
    不可用则自动启动 Chrome (--remote-debugging-port=9222)
    等待 Chrome 就绪（最多 15 秒）
    超时则报错退出
```

## 4. 代码变更

### 4.1 删除模块

| 代码 | 行数 | 原因 |
|------|------|------|
| `STEALTH_SCRIPT` | ~80 行 JS | 真实浏览器不需要伪装 |
| `VIEWPORT_PRESETS` | 7 行 | 使用真实视口 |
| `CHROME_UA_POOL` | 5 行 | 使用真实 UA |
| CDP 层额外注入 | 9 行 | 不需要 |
| `SessionManager.save()` | 减少使用 | Cookie 由 Chrome 管理 |

### 4.2 新增/修改模块

| 代码 | 说明 |
|------|------|
| `_ensure_cdp()` | 检查/启动 Chrome CDP 端口 |
| `_connect_cdp()` | 替代 `_create_context()`，连接真实 Chrome |
| `ensure_login()` | 简化登录检查，依赖 Chrome 已有登录态 |
| `_simulate_browsing()` | 采集前模拟正常用户浏览 Feed |

### 4.3 节奏控制调整

| 操作 | 当前 | 改为 |
|------|------|------|
| 翻页间隔 | 2.5s (高斯) | 3-7s (均匀随机) |
| 笔记详情间隔 | 1.8s (高斯) | 4-10s (均匀随机) |
| 图片下载间隔 | 0.3s (高斯) | 0.5-2s (均匀随机) |
| 采集前浏览 | 无 | 30-60s 随机浏览 Feed |

## 5. 行为层面改进

| 措施 | 说明 |
|------|------|
| 执行频率 | 每天最多 1 次，通过 launchd 定时触发 |
| 采集前浏览 | 随机浏览 Feed 30-60 秒，产生正常行为上下文 |
| 随机休息 | 每 5-10 条笔记后 15% 概率插入 15-60 秒"阅读"停顿 |
| 测试隔离 | 测试使用独立账号，不与日常号混用 |

## 6. 登录流程

```
脚本启动 → 连接 Chrome CDP
         → 检查 xhs.com 是否有 web_session Cookie
         → 有？→ 开始采集
         → 无？→ 打开登录页面
               → 用户手动扫码（在真实 Chrome 中）
               → Cookie 自动持久化到 Chrome profile
               → 后续运行无需重新登录
```

## 7. 风险与缓解

| 风险 | 缓解措施 |
|------|----------|
| Chrome 版本更新导致 CDP 兼容性问题 | Playwright 团队维护 CDP 兼容性 |
| 非 headless 模式影响用户使用 | 用户 Chrome 常驻后台，不影响日常使用 |
| 9222 端口被占用 | 可配置其他端口；兜底脚本可检测多个端口 |
| 采集途中 Chrome 崩溃 | 检查连接状态，重连后继续（从增量记录续传） |

## 8. 测试要点

1. Chrome 以 `--remote-debugging-port=9222` 启动 → 脚本连接正常
2. Chrome 未启动 → 脚本自动兜底启动成功
3. 采集流程完整（收藏列表 → 详情 → 图片 → Markdown 生成）
4. 登录态检查正常
5. 删除增量记录后 --full 模式正常工作
